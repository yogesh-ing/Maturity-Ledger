01 · Overview

Overview & Objectives

AFEC is a privacy-focused personal utility designed to automatically log and monitor expiration timelines (Fixed Deposits, premium accounts, card renewals) by scanning inbound financial SMS. It strips out complex budgeting matrices and focuses strictly on visual time horizons and multi-stage proactive alerts.

03 · Scope

Key Features & Scope

Phase 1 is deliberately narrow: capture, surface, and alert. Everything adjacent to budgeting or bank connectivity is explicitly deferred.

In-Scope — Phase 1

Automatic SMS Parsing

Background monitoring of inbound text messages to detect financial dates (FD maturity, debit/credit card expiry, subscription renewals).

Visual Countdown Dashboard

Big, scannable countdown cards grouped by urgency, showing remaining days at a glance.

Notification Stacking (Multi-Alerts)

Fully customizable pre-alerts (e.g. 14 days, 7 days, 3 days before, and day-of) per instrument or globally.

Manual Entry Fallback

Simple form to manually input or override tracking dates when SMS parsing is unavailable or denied.

SMS Verification Queue

Low/medium-confidence parses are staged for user approval before entering the dashboard, preventing false positives.

Local-First Architecture

Local database storage (Room/SQLite) with zero cloud synchronization to protect financial data privacy.

Home Screen Widget

At-a-glance widget surfacing the single nearest upcoming expiry without opening the app.

Out-of-Scope — Future Phases

  • Automatic account balance tracking or expense categorization.
  • Direct integration with bank APIs (NetBanking / Open Banking / Account Aggregator).
  • Cloud backup or sync across multiple devices.
  • Bill-splitting, budgeting, or investment advisory features.
  • iOS version (Android-only for Phase 1–2 due to SMS API dependency).
Phase 2 candidate: Widget + ExportPhase 3 candidate: Play Store compliant build

Bank SMS arrives → BroadcastReceiver intercepts

Score ≥ 85 → auto-added to Dashboard + toast confirmation

4

Score 50–84 → routed to SMS Verification Queue

Approved item appears on Dashboard, alarms scheduled automatically

3

4

1

Parser extracts an incorrect date or amount

2

Item lands in Verification Queue flagged “Low Confidence”

3

User taps Edit inline, corrects the field

4

Approves corrected entry → feeds anonymized correction back into local heuristic weighting

05 · Experience

Core Screens

Five screens comprise the full Phase 1 surface area of the app.

Screen 01

Countdown Dashboard

Primary landing screen — the single source of truth for all tracked expiries.

  • Sticky header: app title, portfolio summary chip, settings icon
  • Segmented urgency sections: Urgent (≤7d), Approaching (8–30d), Comfortable (31d+), Completed
  • Card: bold title, large day-counter, bank/sub-text, principal amount, color-coded left accent
  • Tap → expands quick actions: Mark Completed / Renew, Edit Details
  • Floating Action Button: + Add Manual
Screen 02

SMS Verification Queue

Holding zone preventing false positives from reaching the dashboard.

  • List of raw SMS beside parsed result card (entity / date / amount)
  • Confidence badge (High / Medium / Low)
  • Inline edit icon for correcting misparsed fields
  • Actions: Approve & Add to Dashboard / Dismiss (swipe or button)
  • Empty state: “You're all caught up” illustration
Screen 03

Manual Entry / Edit Sheet

Bottom-sheet form for adding or editing an instrument by hand.

  • Fields: Title, Institution, Type (FD/Card/Subscription/Other), Amount, Maturity Date (date picker), Notes
  • Per-item alert override toggle (inherit global vs custom)
  • Save / Cancel sticky footer buttons
Screen 04

Alert Settings

Global configuration for the multi-stage notification cascade.

  • Toggle rows: 14 Days Out, 7 Days Out, 3 Days Out, Day-Of (9:00 AM)
  • Custom interval chip input (“Add custom day offset”)
  • Notification channel preview (sound / vibration pattern)
  • Battery-optimization warning card with “Fix it” deep link to system settings
Screen 05

Instrument Detail

Full-screen drill-down for a single tracked item.

  • Large countdown ring/number, maturity date, source (SMS-parsed vs manual)
  • Raw SMS reference (collapsible, for audit trail)
  • History timeline (created, edited, renewed)
  • Primary actions: Renew, Edit, Delete (with confirmation)

SMS Processing Data Flow

SMS Broadcast Receiver

Intercepts SMS_RECEIVED intent

Raw SMS → Room (SmsMessage)

Persisted immediately for audit trail

Regex Date Engine + Confidence Scorer

Keyword, sender & date-format matching

High Confidence ≥ 85

Auto-added to Dashboard + toast

Medium Confidence 50–84

Routed to Verification Queue

Low Confidence < 50

Logged silently, never shown

WorkManager + AlarmManager

Schedules 14d / 7d / 3d / Day-Of alerts at 9:00 AM

Data Model — Room Entities

Four core tables support parsing, tracking, and notification configuration.

schema.kt — entity overview
Entity: TrackedInstrument
├── id: UUID (PK)
├── title: String                     // "HDFC FD Withdrawal"
├── institutionName: String           // "HDFC Bank"
├── instrumentType: Enum              // FD, RD, CARD, SUBSCRIPTION, OTHER
├── principalAmount: Double?
├── maturityDateEpoch: Long
├── source: Enum                      // SMS_PARSED, MANUAL_ENTRY
├── sourceSmsId: UUID?  (FK -> SmsMessage)
├── status: Enum                      // ACTIVE, COMPLETED, DISMISSED, OVERDUE
├── confidenceScore: Int?             // 0-100, null if manual
├── alertOverrides: JSON?             // per-item custom alert offsets
├── createdAt / updatedAt: Long
└── notificationsSent: JSON           // which milestone alerts already fired

Entity: SmsMessage  (raw audit trail, auto-purged after 30 days)
├── id: UUID (PK)
├── rawBody: String
├── sender: String
├── receivedAtEpoch: Long
├── parseResult: Enum                 // SUCCESS, PARTIAL, FAILED
├── extractedFields: JSON
└── userAction: Enum                  // PENDING, APPROVED, DISMISSED

Entity: NotificationPreference
├── id: UUID (PK)
├── alert14Days: Boolean
├── alert7Days: Boolean
├── alert3Days: Boolean
├── alertDayOf: Boolean
└── customOffsets: List<Int>          // e.g. [21, 45]

Entity: ParserPattern  (seed + user-tunable regex heuristics)
├── id: UUID (PK)
├── bankSenderId: String              // "HDFCBK", "SBIINB"
├── keywordSet: List<String>          // ["matures","maturity","expiry","value date","lock-in"]
├── dateRegexTemplate: String
└── baseConfidenceWeight: Int

09 · Engineering

Non-Functional Requirements

Quality attributes the product must satisfy regardless of specific feature behavior.

Performance

  • Cold start under 2 seconds on a mid-tier device (e.g. Snapdragon 6-series).
  • Dashboard list scroll maintains 60fps with 100+ tracked items.

Reliability

  • Scheduled alarms fire within ±1 minute of the target time, including after reboot.
  • Zero data loss on app force-close or OS kill during SMS parsing.

Privacy

  • No network permission requested in Phase 1 — fully offline capable.

Maintainability

  • Unit test coverage ≥ 80% on parser and alarm-scheduling modules.

Accessibility

  • WCAG 2.1 AA color contrast; full TalkBack labeling; 48dp minimum touch targets.

Compatibility

  • Support Android 8.0 (API 26) through Android 14 (API 34), phones and foldables.

11 · Engineering

Security & Privacy Requirements

Given the sensitivity of financial SMS content, security is treated as a first-class, non-negotiable requirement set.

Database Encryption

Room DB encrypted at rest using Android Keystore-backed AES-256-GCM (SQLCipher).

Raw SMS Retention Limit

Raw message bodies auto-purged after 30 days; only structured extracted data persists longer.

Optional App Lock

Biometric / PIN gate before the app content is shown, consistent with other financial utilities.

No Sensitive Logging

Crash reporting and debug logs are scrubbed of account numbers, amounts, and raw SMS text.

Zero Network Permission

Phase 1 requests no INTERNET permission — fully provable offline operation.

Explicit Data Deletion

“Reset Local Data” flow available in Settings with a typed confirmation step.

12 · Engineering

Edge Case Handling

Documented system responses for the scenarios most likely to break trust in an automated parser.

ScenarioSystem Response
Duplicate SMS for same FDMatch on amount + date + sender; update existing record instead of duplicating.
Date already passed on arrivalTag instantly as “Overdue”, surfaced at top of Urgent section in red.
SMS permission revoked mid-useSwitch to manual-entry-only mode; persistent banner explains reduced functionality.
Parser confidence very lowMessage is logged to a hidden “Unprocessed” debug list, never shown to user directly.
Device lacks exact-alarm capabilityFallback to inexact WorkManager periodic checks (~15 min windows).
Dual-SIM deviceApply parsing uniformly across both SIM slots; sender ID matching is SIM-agnostic.
Room database corruptionGuarded migration + 'Reset Local Data' recovery flow with explicit confirmation.
Zero tracked itemsFriendly empty state illustration with primary CTA to add first instrument.

Testing Strategy

A layered QA approach from unit-level regex validation to real-world beta feedback.

Unit Tests

Regex parser validated against 50+ real-world Indian bank SMS templates; date-math edge cases (leap years, month-end).

Instrumentation Tests

BroadcastReceiver injection, Room DAO CRUD operations, WorkManager task execution verification.

Manual QA Matrix

Pixel, Samsung, Xiaomi, OnePlus devices across Android 8–14, including dual-SIM and aggressive battery-saver OEMs.

Security Testing

Verify database-at-rest encryption and confirm no sensitive data appears in logs or crash reports.

Beta UAT

5–10 real users supplying authentic bank SMS to validate parser accuracy before wider rollout.

Google Play policy restricts broad READ_SMS accessHighCriticalShip as sideloaded private build via Android Studio / direct APK; defer Play Store listing to a restricted-permission-compliant Phase 3.
Bank SMS formats change without noticeMediumHighPluggable ParserPattern table; low-confidence fallback always routes to manual approval.
OEM battery optimizers kill background receiverHighHighIn-app whitelisting guide; foreground-service fallback option for power users.
Android version further restricts SMS broadcast accessMediumCriticalManual-entry mode is a fully first-class, not secondary, experience.
User has dual accounts/number changeLowMediumCSV export/import supports manual data migration between devices.
Locale/date ambiguity (DD/MM vs MM/DD)MediumMediumForce India locale date parsing rules; show full written month name on confirmation.

Glossary

FD

Fixed Deposit — a fixed-tenure bank investment instrument.

Confidence Score

0–100 heuristic rating of how certain the parser is that an SMS represents a real financial expiry event.

Verification Queue

Holding area for medium-confidence parsed items awaiting user approval.

Local-First

Architecture principle where all data remains on-device with no mandatory cloud dependency.

Milestone Alert

A scheduled notification tied to a specific day-offset before a maturity date.
